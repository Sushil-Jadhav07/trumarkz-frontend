## Consent contract and UI

- `verificationAPI.getConsentInfo(token)` calls `GET /verification/consent/{token}`.
- `verificationAPI.submitConsentDecision(token, decision)` calls `POST /verification/consent/{token}/decision` with only `{ decision: "accepted" | "rejected" }`.
- The public route is outside authentication guards and renders no dashboard sidebar.
- Pending, server-confirmed unexpired requests show Name, Organization, Batch, Status, the provided deadline, Reject and Allow Verification. Both actions lock during submission, including repeated clicks in the same event turn.
- Accepted requests show Permission Granted and no decision actions. An accepted decision stays final; passing the original response deadline does not revoke permission.
- Rejected requests show Permission Declined and no decision actions. An expired request shows Permission Request Expired and no decision actions.
- On 409, refetch the GET and render its actual current state. An uncertain network/server failure also refetches; the client never invents a successful decision or retries the POST automatically.
- Unknown tokens show Verification Request Not Found without raw backend details. Other errors have an explicit retry state. The browser can refresh information at the persisted deadline, but never writes expiry decisions or creates a new 24-hour period.
- Privacy Policy and Terms of Service link to the existing routes; their content is unchanged.
- Human badges use `consent_status` and `consent_auto_expired`; no null/unknown status badge is fabricated. The deadline is display-only. Product and Warranty records are explicitly excluded.

The existing permissions page is a per-batch wizard, not an organization-default settings form. No new `PATCH /auth/me` behavior was forced into it. Existing `public`/`private` values and batch payloads remain the source of the per-batch override.

**Batch-detail API limitation:** the handoff says `GET /verification/batches/{batch_id}` does not expose consent fields in `users[]`. No consent values were inferred or synthesized there, and no per-user fetch loop was added. The shared details component displays the badge only if its supplied record genuinely has the fields; absence means no badge. OrgDashboard already consumes `/verification/all`, and RecordDetail already consumes `/verification/user/{id}`.

## Organization notifications

- Helpers call only the documented `GET /verification/notifications`, `POST /verification/notifications/{id}/read`, and `POST /verification/notifications/read-all` endpoints. List queries use `unread_only`, `limit=50`, and `offset`.
- Both All and Unread feeds come from the API. The permanent badge and fake records were removed; an API error never substitutes mock data.
- A count below 10 is displayed directly. Counts of 10 or more, or a full page that may have more results, display `9+`; no limited page length is described as a guaranteed total.
- Integration is enabled only for the authenticated organization account. It is not a Super Admin cross-organization inbox. State clears on account/scope changes, and late responses from the previous scope cannot populate the new account's UI.
- Mark-one updates only after API confirmation, does not decrement twice for an already-read row, and reconciles feeds afterward. A mark-one 404 is generic and does not reveal whether another organization owns that ID.
- Mark-all updates both feeds; `marked_count: 0` is valid success. Read and unread filtering use the backend query. Load More uses offsets and does not invent total pages.
- Batch Deleted items show the backend message. Reading one does not navigate to `batch_id`, because that batch can be hard-deleted. View All opens the existing Notifications page.
- Refresh on organization app mount, bell opening, window focus, and every 60 seconds while the document is visible. Timers/listeners are cleaned up. There are no websockets or aggressive polls.
- A successful batch deletion remains successful regardless of optional `notification_created`; existing deletion behavior already satisfies that rule and was not replaced or retried.

## Preserved scope and deployment limitations

Product/Warranty verification behavior, SDC polling, report access rules, public verifier upload/decisions, Dhiway, Super Admin organization management, and legal content were not rebuilt. The consent safeguards below extend the existing action helpers; server-side enforcement remains authoritative.

## Super Admin consent safeguards

- Permission Required Human records enter Smart Send assignments only after `consent_status: accepted`. Pending, declined, automatically expired and missing decisions cannot authorize processing. An accepted decision is not revoked by its original response deadline.
- Batch details omit consent, so the existing batch-filtered `/verification/all` endpoint supplies canonical consent fields in pages of 100. Incomplete, duplicate or wrong-batch responses block the action. There is no request per table row.
- Fresh consent checks run before manual requests, bulk sends, Smart Send, resends, automatic verification, QR/certificate generation and SDC generation/issue. Explicit user selections cannot contain a non-accepted user. Smart Send also refreshes its pending assignments before submission.
- Batch-wide endpoints retain their existing payloads and require at least one accepted user. Their documented backend eligibility filter must continue excluding non-accepted users in mixed batches; the frontend cannot replace that server-side boundary. An empty SDC `user_ids` list retains the existing whole-batch meaning.
- Public Human batch overrides, Product and Warranty do not require consent. Template editing and saving drafts remain available; sending or processing permission-based records requires acceptance.
- Validation: 69 automated tests pass, including actual API-helper checks proving nine processing/send paths make no POST while consent is pending, mixed-user filtering, fresh acceptance, failed refresh, pagination and unaffected batch types. Production build passes. These checks use controlled API responses; real email delivery, backend enforcement and deployed behavior still need environment verification.

The supplied handoff reports that the consent/permission migrations and notification table migration are unapplied, backend changes are undeployed, the expiry scheduler/secret are unconfigured, and SMTP delivery is unverified. Those backend/deployment tasks were not performed here. No internal expiry endpoint or sweep secret is present in frontend source. Live notification creation after an actual batch deletion and real emailed consent links still require end-to-end verification against the correctly migrated/deployed backend. A notification collection 404 surfaces the environment/deployment issue instead of fake data; a consent-token 404 remains the contract's nontechnical invalid-link state.
