# Web push integration report

Implemented against the complete `push_notification_web_trumarkz.md` handoff and the attached frontend brief. Browser push and persisted organization notifications remain separate.

1. **Inspected:** `package.json`, lockfile, `.env` and available env files, `src/`, `public/`, Vite config, AuthContext and every logout caller, AppContext, `useOrganizationNotifications`, the existing bell/page, Profile, route definitions and centralized API interceptors. Searched for Firebase, initialization/config fields, VAPID and service-worker registrations. Read the handoff completely before editing.
2. **Existing Firebase:** none found. No SDK, initialized app, Firebase Web App config or VAPID env variable was present. The handoff's reported Firebase project ID was not converted into an invented runtime configuration. The current bell already uses real backend notifications, despite the older handoff describing a mock implementation.
3. **Created:** `.env.example`; `build/firebaseMessagingWorker.js`; `public/firebase-messaging-sw.js`; `src/lib/firebaseConfig.js`, `firebaseMessaging.js`, `firebaseMessagingWorker.js`, `pushRegistration.js` and their three test files; `src/services/pushNotifications.js`; `src/hooks/usePushNotifications.js`; `src/components/shared/BrowserNotifications.jsx`; this report.
4. **Changed:** `package.json` and lockfile; `vite.config.js`; `src/services/api.js`; AuthContext and AppContext; Navbar, Sidebar and Logout only for awaiting cleanup; Profile and Notifications for the compact control; generated `dist` output. The pre-existing deletion of `dist.zip` was left untouched. Existing notification persistence, polling, read/unread and mark-read functions were preserved.
5. **Dependencies:** official `firebase@12.10.0`, pinned for the existing Node 22 runtime; only modular App/Messaging APIs are imported, lazily. `firebase-admin` was not installed. Explicit `esbuild@0.28.2` generates the worker bundle; Vite keeps its own compatible bundler dependency. A `@grpc/grpc-js >=1.13.6` override addresses the newly added SDK's transitive gRPC advisory. No unrelated dependency major upgrades or `npm audit fix --force` were applied. Other dependency advisories remain outside this change.
6. **VAPID:** read exclusively from `import.meta.env.VITE_FIREBASE_VAPID_PUBLIC_KEY`; no key is hardcoded or supplied by this implementation. `.env` was not overwritten.
7. **Configuration detection:** one allowlisted resolver accepts public config from an existing initialized app or env. An existing default app (or sole named app) is reused. Missing required fields skip initialization. Development diagnostics name missing variables only, once; no values, tokens or raw SDK errors are logged. Optional auth-domain/storage-bucket fields are accepted. Placeholder/blank config values are rejected.
8. **VAPID-only behavior:** app and in-app notifications remain usable; hook reports `configured: false`, `reason: firebase_web_config_missing`; UI says **Not configured**. No `initializeApp`, permission prompt, FCM token generation, worker registration or push-token POST occurs just because a VAPID key exists.
9. **Safely disabled:** real FCM registration, foreground SDK subscription and background push delivery until Web App config and a VAPID key are available. Unsupported browsers/insecure origins/unsupported Firebase browser storage also degrade safely. No Enabled state is inferred from browser permission alone or from listing registered devices.
10. **API helpers:** `pushAPI.registerPushToken(token)` posts only `{token, platform: "web"}` to `/push/tokens`; `getPushTokens()` gets `/push/tokens`; `removePushToken(token)` deletes with an Axios-encoded `token` query parameter. Authentication uses the existing verification client. Optional expected-session guarding cancels stale-account requests before sending. No user ID, org ID or email is sent in these payloads.
11. **Hook/service:** a single AppContext-owned `usePushNotifications` instance wraps the independent registration service. Exposes support/configuration/permission, enabled/loading/error and enable/disable/refresh helpers. Public token pages do not initialize push sessions. Async results and foreground listeners are scoped to the current authenticated session; requests are deduplicated. Only the actual FCM token plus owning user ID are cached for cleanup, never a JWT. Per-account device opt-out survives refresh.
12. **Permission UX:** no prompt on mount. Explicit Enable triggers `Notification.requestPermission()` directly within the user gesture, only when permission is default. Granted permission continues registration; denied permission displays browser-blocked guidance without repeated prompts. Missing config has no misleading enable action. Loading and retry states are provided. Controls are in Profile and Notifications; the bell itself was not rebuilt.
13. **Registration:** already-granted authenticated sessions ensure registration once; focus/visibility changes check for permission/token changes. A real nonempty SDK token and backend metadata acknowledgement are required before Enabled. Explicit refresh can renew backend registration; account switches re-register under current authentication. Token rotation registers the new token before removing the old one. Unsupported/missing-config/tokenless/failed responses never set Enabled.
14. **Logout:** all existing entry points await the central logout function. Push cleanup runs before JWT removal, aborts pending registration, detaches listeners, attempts scoped backend DELETE and SDK token deletion, and clears local token metadata. Cleanup is bounded to three seconds overall and never blocks normal logout on failure. Disabling also records opt-out; failed disable cleanup retains only the minimum information for retry. Backend cleanup remains best effort when the device/network is unavailable.
15. **Worker:** `public/firebase-messaging-sw.js` registers the click handler before importing the generated `firebase-messaging-runtime.js`. The Vite plugin generates a bundled modular Firebase runtime for both dev and build. Its build config is public-only or null, without fake credentials. Existing apps whose public runtime config differs from env pass that allowlisted config in the worker script URL so worker restarts retain it. A missing-config worker never attempts Firebase initialization. Deployment must serve both worker files as JavaScript (not the SPA HTML fallback), over HTTPS or localhost, alongside the app assets.
16. **Foreground:** only backend `notification_type: batch_deleted` messages produce the transient Batch Deleted toast. Message IDs are deduplicated; current-account notifications are refetched using the existing hook. No persistent notification row is created locally. Other event types are ignored.
17. **Background:** Firebase displays notification payloads; data-only batch-deletion messages receive one fallback alert. The wrapper intercepts batch-deletion notification clicks, closes the alert and focuses/navigates an existing same-origin TruMarkZ tab, or opens the organization batch list at `/org/batch-status`. It ignores `batch_id` and remote click URLs, so deleted details are never opened. Real background delivery is **not verified** because no actual Web App configuration is available.
18. **Regression QA:** all configuration, lifecycle, worker-routing and existing utility tests pass. Isolated Chrome checks at 1440px and 390px confirm Not configured, no Firebase app initialization/prompt/token API calls, no horizontal overflow, working in-app read and mark-all (including `marked_count: 0`), and normal logout. The actual Axios helper adapter contract was checked for methods, exact payload, authentication, query encoding and stale-account cancellation. A separately mocked configured flow verified explicit enable, acknowledged registration, foreground toast/refetch without a synthetic history row, and logout DELETE. No production write, real permission prompt or real FCM send was used during QA.
19. **Credentials:** no service-account JSON, private key, Admin credential, bearer-token log or raw FCM-token log was added. Worker generation reads only allowlisted public Web App fields. Test-only fake sessions/configs are confined to tests/mocks; runtime configuration has no fake defaults.
20. **Build:** `npm install` and the actual `npm run build` complete successfully. There is no configured lint script, so none was invented. Existing bundle-size/Browserslist warnings remain. Deploy generated `dist/firebase-messaging-sw.js`, `dist/firebase-messaging-runtime.js` and all application assets together; no deployment was performed here.
21. **Still needed later:** `VITE_FIREBASE_API_KEY`, `VITE_FIREBASE_PROJECT_ID`, `VITE_FIREBASE_MESSAGING_SENDER_ID`, `VITE_FIREBASE_APP_ID` (required for Messaging), plus `VITE_FIREBASE_AUTH_DOMAIN` and `VITE_FIREBASE_STORAGE_BUCKET` (supported optional Web App fields). `VITE_FIREBASE_VAPID_PUBLIC_KEY` must also be added; it was not present in the inspected env. All must belong to the correct Firebase project; rebuild/redeploy after adding them. No request for these values was needed to finish this implementation. Backend token-table migration, sender credentials/IAM, production deployment and actual end-to-end inbox/OS delivery remain unverified backend/ops prerequisites from the handoff.

- Production build passed and emitted both worker files. Real FCM delivery remains untested and disabled until real project configuration is added.
